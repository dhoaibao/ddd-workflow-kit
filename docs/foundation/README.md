# DDD foundation

This learning set introduces Domain-Driven Design as a way to align software models with a business domain. It is intentionally framework- and language-neutral. DDD can inform a modular monolith, separately deployed services, or another architecture; it is not a synonym for microservices.

## Suggested path

1. [Fundamentals](01-fundamentals.md): purpose, language, and the problem space.
2. [Strategic design](02-strategic-design.md): domains, subdomains, bounded contexts, and context maps.
3. [Tactical design](03-tactical-design.md): models and building blocks used inside a context.
4. [Implementation approaches](04-implementation-approaches.md): architecture and delivery choices.
5. [Adoption playbook](05-adoption-playbook.md): greenfield and brownfield workflows.
6. [Pitfalls and best practices](06-pitfalls-and-best-practices.md): trade-offs and checklists.
7. [Glossary](glossary.md) and [references](references.md): terminology and further reading.

## How to use this material

Treat DDD as a set of modeling and collaboration tools rather than a mandatory recipe. Start with the business problem, make assumptions explicit, validate terms with domain experts, and choose only the patterns that reduce a demonstrated risk. Models are hypotheses that should be revised as understanding changes.
