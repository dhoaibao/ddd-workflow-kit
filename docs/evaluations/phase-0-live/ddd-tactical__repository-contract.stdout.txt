RESULT

- **Scope:** Approvals context, capability of recording approval decisions, selected slice: approving one pending request.
- **Outcome:** Approve one pending request safely.
- **Command/use case:** `Approve pending request`
  - **Actor:** Not specified; approval workflow is the available provenance.
  - **Preconditions:** The request is pending. The approval root is retrieved through its external access point.
  - **Inputs:** A request/approval identity and the approval decision; exact input shape is not specified.
  - **Decision:** Verify that the request is still pending, then record the approval decision.
  - **Successful outcome:** The approval decision is recorded and the approved fact is available for Settlement.
  - **Failures:** Missing request reporting is unresolved. An optimistic concurrency conflict must fail safely rather than overwrite a concurrent decision.
  - **Counterexample:** Two concurrent approval attempts must not both replace or create competing current decisions.
  - **Observable acceptance signals to define:** One current decision remains; stale saves are rejected; Settlement can consume the resulting approved fact.
  - **Affected relationship:** Settlement consumes approved facts.

- **Invariant:**
  - `Only one approval decision is current.`
  - **Evidence:** Candidate invariant and invariant supplied in the strategic handoff; supported by the concurrent-update failure evidence.
  - **Scope/owner:** Approval root; Approvals owner.
  - **Failure consequence:** Conflicting or stale approval state could be persisted and consumed by Settlement.
  - **Validation:** Validated as a candidate domain invariant; the precise lifecycle rules for pending, approved, rejected, and superseded decisions remain unspecified.
  - **Consistency:** Immediate within the approval aggregate transaction. Optimistic concurrency is required to prevent lost updates.

- **Model elements:**
  - **Approval aggregate/root:** Proposed and evidence-backed. The root is the external access point and is the smallest identified boundary protecting the “one current decision” invariant.
  - **Approval decision:** Domain state/value within the approval root. Whether it is a separate entity or value object is unresolved because identity and lifecycle details are not provided.
  - **Repository:** Required for the named need to retrieve and save one approval aggregate root. The contract is domain-facing:
    - retrieve the approval root by its domain identity;
    - report absence according to an unresolved missing-request policy;
    - save the root with an optimistic version or equivalent concurrency token;
    - reject stale saves with a domain/application-visible concurrency conflict;
    - preserve the invariant on successful save.
    - No persistence technology, schema, ORM, database, or implementation is selected.
  - **Domain service:** Not needed based on current evidence; the decision appears to belong to the approval root.
  - **Specification/factory:** Not needed; no named rule requires either.
  - **Domain event:** `ApprovalDecisionRecorded` is proposed as a past-tense fact if Settlement integration requires publication. Its exact payload and publication obligation are unresolved.

- **Application flow:**
  1. Retrieve the approval root through the repository.
  2. If absent, apply the unresolved missing-request policy.
  3. Ask the root to approve the pending request.
  4. Save using optimistic concurrency.
  5. If the version is stale, reject the operation; do not silently retry an approval decision without an explicit policy.
  6. Publish or otherwise expose the approved fact for Settlement according to an integration contract that remains to be defined.

- **Consistency and concurrency:**
  - The “one current decision” invariant is immediate within the approval root.
  - Settlement consumption may be eventual if approval facts are delivered asynchronously; this is an integration assumption, not yet a validated policy.
  - Delivery ordering, duplication, idempotency, retry, recovery, privacy, and exact event transport are unresolved.
  - Repository save must provide optimistic conflict detection. Automatic conflict retries are not assumed.

- **Persistence:**
  - Persistence technology is intentionally unspecified.
  - The repository abstracts retrieval, save, absence, and optimistic-conflict semantics only.
  - No database, schema, ORM mapping, transaction mechanism, or deployment decision is implied.

- **Optional patterns:**
  - **CQRS:** `not-needed` for this slice; no evidence requires separate read/write models.
  - **Event sourcing:** `not-needed`; ordinary domain facts do not imply event sourcing, and no history/replay requirement is supplied.

- **Expected outcomes addressed:**

  - The repository contract includes optimistic conflict handling.
  - The approval root is the external access point.
  - The one-current-decision invariant is protected immediately within the root.
  - Persistence technology remains unspecified.
